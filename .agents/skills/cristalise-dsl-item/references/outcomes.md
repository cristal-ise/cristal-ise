# Outcome Reference

This file documents the `Outcome` DSL construct for linking Schemas to Items for data storage and retrieval.

## Overview

An **Outcome** is data obtained during the execution of an Activity. Outcomes must conform to a Schema and can be submitted by users or generated by Scripts. The `Outcome` DSL construct links a Schema to an Item, defining where and how outcome data is stored.

## Purpose

Outcome references serve several purposes:
- Link a Schema definition to an Item for data validation
- Define the storage path for outcome XML files
- Enable data retrieval through the outcome system
- Support versioning of outcome data

## Syntax

There are two forms of the `Outcome` declaration:

### Form 1: Using Bound Variable

```groovy
Outcome($schema_PropertyDescriptionList)
```

This form uses a pre-bound Schema variable. The `PropertyDescriptionList` is a special Schema that defines metadata properties.

### Form 2: Explicit Parameters

```groovy
Outcome(schema: 'SchemaName', version: 0, viewname: 'last', path: 'boot/module/SchemaName_0.xml')
```

This form explicitly specifies all parameters.

## Parameters

**schema** (String, *required*): The name of the Schema that defines the structure for this outcome. The Schema must exist in the system.

**version** (Integer, *required*): The version of the Schema to use. Must match the Schema's version.

**viewname** (String, *optional*, default: `'last'`): The name of the Viewpoint (named version) for this outcome. The special value `'last'` always points to the most recent outcome version.

**path** (String, *optional*): The file path where the outcome XML is stored. If not specified, a default path is generated based on the Schema name and version.

## Multiple Outcomes

An Item can have multiple Outcome declarations, each linking to a different Schema:

```groovy
Item(name: 'Customer', folder: '/module/CRM', workflow: $customer_Workflow) {
    InmutableProperty('Type': 'ImportItem')
    
    // Primary outcome for customer data
    Outcome(schema: 'Customer', version: 0, viewname: 'last', path: 'boot/crm/Customer_0.xml')
    
    // Secondary outcome for audit data
    Outcome(schema: 'CustomerAudit', version: 0, viewname: 'last', path: 'boot/crm/CustomerAudit_0.xml')
    
    // Metadata outcome
    Outcome($customer_PropertyDescriptionList)
}
```

## Binding and Variables

Outcomes can reference variables bound in the DSL context:

```groovy
// Using a bound PropertyDescriptionList
def customerProps = // ... PropertyDescriptionList definition

Item(name: 'Customer', folder: '/module/CRM', workflow: $customer_Workflow) {
    InmutableProperty('Type': 'ImportItem')
    Outcome($customerProps)
}
```

## Common Patterns

### Standard Item Outcome

```groovy
Outcome(schema: 'MyItem', version: 0, viewname: 'last', path: 'boot/module/MyItem_0.xml')
```

### Property Description Outcome

```groovy
Outcome($myItem_PropertyDescriptionList)
```

### Multiple Versioned Outcomes

```groovy
Outcome(schema: 'MyItem', version: 0, viewname: 'v1', path: 'boot/module/MyItem_v1.xml')
Outcome(schema: 'MyItem', version: 1, viewname: 'last', path: 'boot/module/MyItem_1.xml')
```

## Best Practices

1. **Always Include**: Every Item should have at least one Outcome for data storage
2. **Use PropertyDescriptionList**: Include `Outcome($..._PropertyDescriptionList)` for metadata
3. **Consistent Paths**: Use consistent path naming conventions (e.g., `boot/module/Name_Version.xml`)
4. **Viewpoint 'last'**: Always include a `viewname: 'last'` outcome for accessing the most recent version
5. **Schema Version Match**: Ensure the Schema version matches the actual Schema definition

## Path Conventions

Recommended path structure for outcomes:

```
boot/
  {module}/
    {ItemName}_{version}.xml
```

Example:
```groovy
Outcome(schema: 'Customer', version: 0, viewname: 'last', path: 'boot/crm/Customer_0.xml')
```
